# 亚马逊店铺 AI 运营体系 — 设计方案

> 2026-08-29。前提：品牌方负责产品、合规、退换货成本；**你只负责运营**。
> 目标：把店铺搭起来并跑成一套体系，**且不吃掉你大量时间**。

---

## 一、核心设计原则

"不占精力"不是靠全自动，是靠**把工作分成三类，只留一类给自己**。

| 类型 | 谁做 | 例子 |
|---|---|---|
| **一次性搭建** | 前期重投入，做对了后面省一年 | 变体结构、listing 骨架、关键词矩阵 |
| **重复性判断** | **只有你能做，也必须你做** | 调价、加减广告预算、要不要清库存 |
| **重复性搬运** | **全部交给 AI** | 拉数据、算指标、写周报、起草客服回复、盯竞品 |

**大部分人累，是因为把第三类当成第二类在做。**

体系的目标就一句话：**AI 负责"收集 + 起草 + 提议"，你负责"决策 + 确认"。**

---

## 二、数据地基：什么能自动拿，什么拿不到

（2026-08-29 查证，非既有知识。这一节决定了后面哪些环节能真自动化。）

### ✅ SP-API 能自动拉

订单 / 库存 / **退货报告** / 销售与流量报告（含 Buy Box 占比、页面浏览量）/
listing 增删改 / 付款 / 店铺评价 / **搜索词报告** / 市场篮分析 / 复购分析。

广告数据走 **Amazon Ads API**（独立于 SP-API）。

**前提**：品牌方的账号必须是专业卖家，并授权你的 SP-API 开发者身份。
**这条要写进合作条款——拿不到授权，整个体系降级成手工活。**

### ⚠️ 半自动（有办法但不优雅）

- **买家消息**：SP-API Messaging 是 **send-only**，读不到买家发来的内容。
  只能靠 Amazon 的邮件通知转发（自建解析，或用 ChannelReply 这类桥接工具）
- **竞品数据**：官方无接口。靠 Helium 10 / Jungle Scout 这类工具，或自己抓

### ❌ 拿不到

- **商品评论内容**。Amazon 早就关掉了评论 API，SP-API 里的 "feedback" 是**店铺评价**，
  不是产品评论。
  **影响**：评论是这个品类最宝贵的情报源（买家会直接写"尺码偏小两号"），
  但只能靠第三方工具或人工定期扒。**这是体系里唯一一个必须留人工口子的地方。**

## 三、阶段 0 · 搭建期（签约后 4–6 周，一次性重投入）

**这一阶段 AI 杠杆最大，而且完全不需要账号权限——现在就能开始。**

### 3.1 竞品与关键词研究 → 这是所有后续工作的原料

**AI 干的**：
- 扒 10–15 个直接竞品的：价格带、评分、review 数、主图策略、五点结构、变体设置
- **重点扒差评**：把竞品所有 1–3 星评论抓下来，按抱怨类型归类统计

**为什么差评最值钱**：竞品的差评就是**免费的、真实的、已验证的用户调研**。
在这个品类里，你几乎一定会看到大量"尺码偏小/偏大""袖子太短""洗几次就不防晒了"。
**每一条高频抱怨，都是你的 listing 上该主动回答的问题，也是你降退货率的靶心。**

**你干的**：看归类结果，判断哪几条是这个品牌能打的差异点。

### 3.2 Listing 生成

**AI 干的**：基于关键词矩阵 + 差评洞察，生成标题 / 五点 / A+ 内容大纲 / 图片脚本 /
后台搜索词。**每一条五点都对应一个真实的买家顾虑，不写空话。**

**你干的**：审、改、定。**UPF 相关文案必须对着测试报告逐条核**（见评估文档第一节）。

### 3.3 变体结构设计 ← 最容易埋雷的一步

尺码 × 颜色 × 厚度的父子关系一旦建错，**后面改动成本极高，评论还会丢**。

**AI 干的**：给出 2–3 种变体结构方案 + 各自的优劣。
**你干的**：定。这一步值得多花时间。

### 3.4 尺码与厚度知识库 ← 后面所有环节的地基

把品牌方给的尺码表、厚度-水温对照、面料说明，整理成**结构化数据**（不是 PDF）。

**这份数据同时喂给三个地方**：listing 文案、客服助手、退货分析。
**它是整个体系的核心资产。**

## 四、阶段 1 · 上线期：客服助手（降退货，不是省人力）

详见评估文档第四节。要点：

- **主战场是售前尺码/厚度咨询**，因为退货率是这个品类的利润杀手，
  而退货的决定发生在**买之前**
- 形态：**AI 起草 → 标注依据来源 → 你一键确认发出**
- 这个形态不是妥协，是 2026 Amazon AI 代理政策的**强制要求**（Tier 2 需人工检查点 +
  审计日志 + 速率限制）

**你的日常投入：每天 10–15 分钟确认草稿。**

## 五、阶段 2 · 运营期：一周一次的固定节奏

**这一节是"不占精力"的答案。**

### 每周一次「运营例会」，60 分钟，你只做决策

**AI 在你打开之前已经做完的**：

1. 拉齐上周所有数据（销售 / 广告 / 退货 / 搜索词 / 库存 / Buy Box）
2. 算出关键指标和环比变化
3. **归类上周的退货原因**（退货报告里有买家选的原因 + 备注）
4. 扫一遍竞品价格和 listing 变动
5. 输出一份周报，最后给 **3–5 条具体建议，每条附数据依据和预期影响**

**你做的**：看结论，对每条建议点"采纳 / 否决 / 再看看"。

**关键设计**：建议必须是**可执行的具体动作**（"把 XX 关键词的竞价从 $1.2 降到 $0.9，
上周它花了 $87 转化 0 单"），不是"建议优化广告结构"这种废话。

### 每月一次「listing 迭代」，2 小时

这是让体系**越跑越好**的闭环：

```
退货原因 + 评论抱怨
      ↓
  找出高频问题（例：M 码退货率是其他码的 3 倍）
      ↓
  改 listing / 改尺码表 / 改主图
      ↓
  下月退货率下降 → 省下退货处理费
      ↓
  （数据回流，继续迭代）
```

**这个闭环是整套体系里最值钱的东西。** 它把"客服"和"listing"从两件事变成一件事，
而且效果可量化——**你可以拿退货率的下降曲线去跟品牌方谈续约和涨价。**

### 时间总账

| 频率 | 事项 | 耗时 |
|---|---|---|
| 每天 | 确认客服草稿 | 10–15 分钟 |
| 每周 | 运营例会（看周报、做决策） | 60 分钟 |
| 每月 | listing 迭代 | 2 小时 |
| 不定期 | 突发（账号问题、A-to-z 索赔、大促） | — |

**稳态约每周 3–4 小时。** 搭建期例外，那 4–6 周要重投入。

| 层 | 用什么 | 干什么 |

**这不是巧合。** 纲要里定的骨架本来就是为这类活选的——现在有了真实项目，
每一层都有了明确用途。

## 七、落地顺序（按店铺生命周期，不是按技术难度）

| 顺序 | 做什么 | 为什么是这个时候 | 需要账号权限吗 |
|---|---|---|---|
| **1** | 竞品差评挖掘 + 关键词研究 | 签约前就能做，且是所有后续的原料 | ❌ 不需要 |
| **2** | 尺码/厚度知识库 | listing 和客服都依赖它 | ❌ 只需品牌方资料 |
| **3** | Listing 生成 | 上架前必须完成 | ❌ |
| **4** | 客服助手 | 一上线立刻有咨询和退货 | ✅ 需要（邮件转发） |
| **5** | 周报引擎 | 有订单数据了才有得报 | ✅ 需要 SP-API |
| **6** | 迭代闭环 | 攒够 1–2 个月数据才跑得动 | ✅ |

**第 1 步今天就能开始，不用等签约。** 而且做完第 1 步，你手上就有了一份
**基于真实竞品差评的品类分析**——这本身就是谈判桌上最有说服力的东西。

## 八、基础设施与隔离

### Docker 解决不了抓取的风险

| 工具 | 隔离什么 | 对账号关联风险有用吗 |
|---|---|---|
| venv | Python 包 | ❌ 无关 |
| **Docker** | 文件系统、进程、依赖 | ❌ **容器默认走宿主机网络出口，公网 IP 是同一个** |
| **独立服务器 / 代理** | **网络出口 IP** | ✅ **这才是要隔离的东西** |

**风险的本质是 IP 关联**——Amazon 看到同一个 IP 既在高频抓商品页、又在登录某个卖家后台。
Docker 装得再干净，流量还是从同一条宽带出去。

### 四条隔离的具体做法

1. **独立出口 IP** ← 唯一真正重要的一条
   最便宜的云服务器（Vultr / DigitalOcean / 阿里云香港，**$5–6/月**），抓取跑在上面
2. **设备与登录态隔离**
   那台服务器**永远不登录 Seller Central**；日常登录后台的 Mac **永远不跑抓取**。
   这条是纪律不是技术，但比技术重要
3. **温和速率**：随机间隔 3–8 秒、单线程。一晚上慢慢跑完够用
4. **只抓公开页、只做一次性调研**。长期跑的东西才容易被盯上

### Docker 的正确用途：可复制，不是安全

打包环境，换台服务器一条命令起来。**第一版别上 Docker**——一台 VPS + 一个脚本先把活干成，
等要复用到第二个客户时再打包。

## 九、可复制：从"运营一个店"到"代运营产品化"

> 这一节是 2026-08-29 用户提出的真正目标：**标准化、可复制**。
> 设计目标完全不同——不是把这个店做好，是**做一套接下一个客户时能直接套用的东西**。

### 核心结构：一套代码 + 每客户一份配置

```
agency-os/
  core/                    ← 所有客户共用，只写一次
    scrape/                竞品与评论抓取
    analyze/               差评归类、关键词、退货原因分析
    listing/               listing 生成
    support/               客服起草
    report/                周报引擎
    sp_api/                Amazon 接口封装
  clients/
    brand-a/
      config.yml           ← 品类、站点、竞品 ASIN、语气、品牌禁用词
      knowledge/           ← 尺码表、厚度对照、材质、合规文件
      data/                ← 该客户的历史数据（SQLite）
      outputs/             ← 生成的 listing、周报、分析
    brand-b/
      （同样结构）
```

**新客户上手 = 建一个文件夹 + 填一份 config + 灌知识库。** 代码一行不改。

### 每个客户必须齐备的五份资产（缺一个体系就跑不动）

| 资产 | 从哪来 | 缺了会怎样 |
|---|---|---|
| 1. **config.yml** | 你填 | — |
| 2. **尺码 / 规格知识库**（结构化，非 PDF） | 品牌方 | 客服答不了、listing 写不准 |
| 3. **合规文件**（AS 4399 测试报告等） | 品牌方 | 文案不敢写、有下架风险 |
| 4. **竞品 ASIN 清单** | 第 1 步产出 | 无法做对比和监控 |
| 5. **SP-API 授权** | 品牌方 | 周报引擎降级成手工 |

**这份清单本身就是新客户的入场问卷。** 拿不齐的客户，要么补齐要么别接——
这是你以后筛客户的标准。

### 自动化的投入产出排序

按"每投入 1 小时能省多少小时"排，**别按技术难度排**：

| 优先级 | 模块 | 每客户省多少 | 复用性 |
|---|---|---|---|
| **1** | **差评分析 + listing 生成** | 每个客户上手期省 **20–30 小时** | ⭐⭐⭐ 每来一个新客户就复用一次 |
| **2** | **客服起草** | 每天 1–2 小时，长期累积最大 | ⭐⭐⭐ 换客户只换知识库 |
| **3** | **周报引擎** | 每周 2–3 小时 × 客户数 | ⭐⭐⭐ 客户越多越值 |
| 4 | 竞品监控 | 每周 1 小时 | ⭐⭐ |
| 5 | 广告自动调价 | 视规模 | ⭐ 风险高，最后做 |

**第 1 项排第一不是因为省得最多，是因为它是每个新客户的第一件事**——
做好了，第二个客户的上手期从一个月压到一周。**这才是"可复制"的真实含义。**

### 关键设计纪律：什么绝不自动化

**永远保留人工的**：调价、广告预算增减、账号申诉、A-to-z 索赔、发给买家的最终确认。

理由不只是合规（2026 政策强制人工检查点），是**风险不对称**：
自动化省下的是几分钟，一次自动调价失误可能烧掉几千块或引来账号问题。

**AI 负责"收集 + 起草 + 提议"，你负责"决策 + 确认"** —— 这条在多客户下更重要，
因为你的注意力被摊薄了，而每个错误的代价没变小。

### 客户数量与时间的关系

| 客户数 | 每周你的时间 | 前提 |
|---|---|---|
| 1 | 3–4 小时 | 体系跑通 |
| 3 | 8–10 小时 | 第 1–3 项自动化全部就位 |
| 5+ | 需要招人 | 你的角色转成审核与决策 |

**从 1 个到 3 个客户，边际时间是递减的**——因为搭建成本已经付过了。
**这就是代运营这门生意能不能规模化的分水岭。**

## 十、开始第 1 步需要什么

已确定：**主推防晒衣 + 潜水服，目标 amazon.com.au，自己写抓取脚本。**

还差两个决定：

1. **抓取方式**：先手工/半自动跑一轮验证分析价值，还是直接上 VPS + 脚本
2. **VPS 供应商**：如果直接上脚本，选哪家（我建议 Vultr 或 DigitalOcean，$6/月，
   十分钟开好）

**数据源已按澳洲站调整**（见 `australia-market-brief.md`）：
美国站扒差评补数据量，澳洲站扒价格与竞争格局。
