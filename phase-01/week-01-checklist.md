## 怎么用这份清单

每一条都有三栏，**第三栏是重点**：

| 栏 | 作用 |
|---|---|
| 动作 | 做什么 |
| 命令 | 照着敲什么 |
| **怎么证明做完了** | **看到什么才算这一步过了。看不到就是没做完，不许往下走** |

第三栏是 2026-08-18 Day 2 之后加的。那天有一条修复措施——发现了、讨论了、说好要改——
**然后没人执行，流程继续往下走了**，直到回头看截图才发现。

**交付里最常见的事故不是没发现问题，是发现了、说好要改、然后没人回头确认改没改。**
所以每条都要能被证明，"我记得我做了"不算证明。

## Day 2 — 第一次调用 Claude API ✅ 2026-08-20 完成

**顺序不能乱**：先建黑名单，再放 key。反了的话 Git 可能已经追踪上那个文件，
后补 `.gitignore` 是不管用的。

| # | 动作 | 命令 | 怎么证明做完了 |
|---|---|---|---|
| 1 | 申请 API key | 上 console.anthropic.com → API keys → Create Key | 拿到 key（只显示这一次，先复制好） |
| 2 | **先**建黑名单 | `echo ".env*" >> .gitignore`<br>`echo "venv/" >> .gitignore` | `cat .gitignore` 能看到这两行 |
| 3 | **再**存 key | `nano .env`，写 `ANTHROPIC_API_KEY=你的key`<br>存盘：`^O` → 回车 → `^X` | `wc -l .env` 输出 `1`（**用 wc 不用 cat**，避免 key 打印到屏幕上） |
| 4 | **去看现场** | `ls -a` | 只该有 `.env`、`.gitignore`、`venv`。**看到任何多出来的文件都要查清楚** |
| 5 | 确认没泄露 | `git status` | 报 `not a git repository` 说明还没版本管理，安全；<br>如果已经是仓库，**输出里绝不能出现 `.env`** |
| 6 | 装 dotenv（先过卡点 1） | `pip install python-dotenv` | `python3 -c "import dotenv; print('ok')"` 打印 ok<br>（装用 `python-dotenv`，import 用 `dotenv`，名字不一样是正常的） |
| 7 | 写脚本 | `nano hello_claude.py` | nano 底部显示 `[ Wrote N lines ]` |
| 8 | 跑通 | `python3 hello_claude.py` | **屏幕上出现模型回复的一句话** |

### 第 4 步为什么单独列出来

Day 2 当天，第 2、3 步都做对了，但 `ls -a` 抓到一个 `.env.save`——nano 被中断时留下的
应急备份，里面同样有 key，而当时的 `.gitignore` 只写了 `.env`，覆盖不到它。

**这个洞不在任何清单上，是"去看现场"抓出来的。**

清单是人写的，人想不到的事就不会在清单上。所以每天都要有一步是**实际去看有什么**，
而不只是核对预期中的东西。这就是五步方法论里「验收 Harden」存在的理由。

（第 2 步现在直接写 `.env*` 通配，就是这次的修复——`*` 覆盖所有以 `.env` 开头的文件，
比逐个列举可靠。）

2. 包名逐字核对（typosquatting 就是靠差一个字母骗你装错）
3. 风险中/高时，有没有附上实际查到的东西（版本、发布日期、维护者、许可证）

## 排错：`command not found` 四步

按顺序想，别跳：

1. **拼写对吗**（最常见，也最容易被跳过）
2. **该激活的环境激活了吗**（看提示符有没有 `(venv)`）← Day 2 卡在这条
3. **这个东西真的装过吗**
4. `which 命令名` —— 它会告诉你系统找到的是哪一个，或者干脆找不到
