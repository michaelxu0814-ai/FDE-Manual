# Phase 01 · Week 4 — 交付：让客户真正能用上（部署）

场景收官：界面 Week 3 已经做出来了，但它只跑在你自己的电脑上。客户要的是——发一个 URL，
他们在哪都能打开用。Week 4 的目标：把整套东西部署到公网，按"验收→交付"的标准走完，
Phase 1（电商客服助手）正式收官。

每天 1 小时。做不完没关系，宁可少而扎实，也不要囫囵吞枣往下赶。

## Day 1 — 概念：部署是什么

**目标**：搞懂"本地跑"和"上线"的区别，不急着动手。

- 概念：部署 = 把应用放到一台"一直在线、有公网地址"的服务器上。客户输 URL 就能用，
  不依赖你的电脑开没开。
- 概念：为什么不能直接把你的电脑当服务器（会关机、IP 会变、密钥和数据库放私人电脑不安全）。
- 让 Claude Code 用大白话讲一遍：Railway/Vercel 这类平台到底帮你做了哪几件事。
- 输出：你能口头讲清楚"部署要做哪三件事"（整理依赖、密钥进环境变量、代码推到 GitHub）。

## Day 2 — 部署前的准备

**目标**：把项目收拾到"能交给平台"的状态。

- 整理 `requirements.txt`（项目依赖清单，服务器要按它重装）。
- 把 API key 等密钥从代码里挪到环境变量（代码里只留名字，不写值）。
- 把 Week 3 的项目推到 GitHub（平台从仓库拉代码）。
- 概念：**环境变量** = 运行环境注入的配置，换环境不用改代码，密钥也不跟仓库走。

## Day 3 — 在 Railway 部署，拿到公网 URL

**目标**：客户真正能打开的那个链接，落在你手里。

- 注册/登录 Railway（或用户指定的平台），新建项目，连接 GitHub 仓库。
- 把密钥配置到平台的环境变量里（在网页后台填，不写进代码）。
- 触发部署，等构建完成，拿到公网 URL。
- 让 Claude Code 带你读部署日志，搞懂"构建→启动→就绪"每一步在干什么。

## Day 4 — 验收：用客户的眼睛测一遍

**目标**：按"验收（Harden）"标准走一遍，再写交付说明。

- 用手机（不是桌面浏览器）打开 URL：能提问、能看到带出处的回答、空输入不崩、答不上来会直说。
- 检查：日志里有没有报错；密钥有没有泄到任何地方（仓库、代码、页面）。
- 写"交付说明"（给客户的一页纸）：URL、怎么用、已知限制、出问题找谁。
- 概念：Build（能跑）和 Harden（经得起用）的区别——客户要的是后者。

## Day 5（周五）— 复盘 + Phase 1 收官

- 自测本周概念 + 回顾整个 Phase 1（对照 w1-w4 闪卡）。
- 用五步方法论把客服助手项目完整串一遍：摸底→架构→搭建→验收→交付，每步的产出是什么。
- 把"交付说明"整理成一份文档，放进 `fde-week4` 留档。
- 问自己：如果现在来一个新客户，我能不能独立走一遍？（能 + 哪里不行，都记下来。）

## Day 6-7（周末，轻量/可选）— 缓冲

- 把 Phase 1 没啃完的地方补上，或休息。Week 5 进入 Phase 2（运营自动化流程），会有新的挑战。
