# Phase 01 · Week 1 — 环境与第一次调用

场景提醒：一家中型电商公司，客服团队被重复问题淹没，想要一个能根据产品手册和常见问题
自动回答客户的助手。Week 1 不碰这个场景本身，先把"能调用大模型"这件事的地基打好——
后面三周才真正开始搭这个客服助手。

每天 1 小时。做不完没关系，宁可少而扎实，也不要囫囵吞枣往下赶。

## Day 1 — 环境搭建

**目标**：一个能跑 Python 脚本的干净环境。

- 确认电脑上有 Python（终端跑 `python3 --version`；没有就装）
- 建一个项目文件夹 `fde-week1`，在里面建一个虚拟环境（`python3 -m venv venv`）
- 装一个包试试（`pip install anthropic`），确认能装上、能 import
- 让 Claude Code 带你做，但每一步都问它"这一步在干什么、为什么要这一步"，不要只是复制粘贴命令

**今天不需要懂**：虚拟环境背后的原理细节。先能用，原理留到 Day 3。

### 延展 · 你没问但该知道的

**1. 虚拟环境工具不止 venv 一个**
venv 是 Python 自带的、最基础的那个。同类的还有 virtualenv（venv 的前身，功能重叠）、
conda（数据科学圈常用，还能管非 Python 的依赖）、poetry / uv（更现代，把虚拟环境 + 依赖
版本锁定 + 打包发布整合在一起，uv 是这两年增长最快的）。
**关系**：它们都是 venv 的同类替代品，底层思路一样——"给项目一个独立的包安装空间"。
**什么时候碰到**：进公司或接手别人的项目时，对方用什么你就得跟着用。
**现在要不要管**：不用。先吃透最基础的 venv，其它工具是在这个基础上加功能，以后换很快。

**2. Docker：比虚拟环境大一圈的隔离**
venv 隔离的是"Python 包"；Docker 隔离的是"整台机器"——操作系统、系统级软件、Python
本身的版本，全打包进去。
**关系**：Docker 是 venv 的上一层，解决 venv 解决不了的问题："在我电脑上明明能跑啊"。
**什么时候碰到**：Phase 03 企业级交付时，客户问"这东西怎么部署到我们自己的服务器上"，
Docker 就是标准答案。
**现在要不要管**：不用。我们的部署走 Railway / Vercel，这类平台会替你处理运行环境。
知道 venv 管包、Docker 管整个环境这个分层就够了。

**3. `pip` 和 PyPI：包是从哪来的**
`pip install anthropic` 时，包是从 PyPI（pypi.org，Python 官方的公共包仓库）下载的，
任何人都能往上面发布包。
**关系**：pip 是"装包的动作"，PyPI 是"包存放的地方"，venv 是"包装到哪里"。
**什么时候碰到**：想确认一个包是不是官方的、有多少人在用、最后更新是什么时候——上 pypi.org
搜包名看。业界真出过"发布同名恶意包骗人装错"的事（叫 typosquatting）。
**现在要不要管**：习惯上要管。以后装陌生的包之前，花十秒去 pypi.org 扫一眼，这是安全纪律
的一部分，跟"API key 不写死在代码里"是同一类习惯。

## Day 2 — 第一次调用 Claude API

**目标**：命令行里跑出模型的第一句回复。

- 去 console.anthropic.com 申请一个 API key（这是你自己要做的一步，不是 Claude Code 能替你做的）
- 写一个最短的脚本：发一句话给模型，把它的回复打印出来
- 跑通它——看到模型真的回了一句话

**今天要注意**：把 API key 存在环境变量或本地文件里，不要写死在脚本里、不要传到任何地方。
这是你以后做企业交付时"数据/密钥不能明文"这条纪律的第一次练习，从今天开始养成。

### 延展 · 你没问但该知道的

**1. 大模型不止 Claude，接入方式是通的**
同类的还有 OpenAI 的 GPT、Google 的 Gemini、开源的 Llama / Qwen 等等。
**关系**：它们都是 Claude API 的同类替代品，调用方式高度相似——都是发 HTTP 请求、
都有 messages/role 这套结构。学会一个，换另一个只需要改几行。
**什么时候碰到**：客户可能已经有 OpenAI 的账号、或者因为数据合规要求必须用国内模型。
FDE 要能说清"为什么这个场景选这个模型"，而不是只会一种。
**现在要不要管**：不用。三个月内技术骨架固定用 Claude，专注把一条路走透。

**2. API key 泄露是真实事故，不是理论风险**
key 一旦进了 GitHub 公开仓库，会在几分钟内被自动扫描机器人捡走盗刷——业界每年都有人
因此收到几千美元账单。
**关系**：这就是今天"不要写死在代码里"这条纪律背后的真实后果。
**什么时候碰到**：以后每一个项目。工程上的标准做法是 `.env` 文件存 key + `.gitignore`
把它排除在版本管理之外（Day 2 就会用到，`.gitignore` 是 Git 里"这些文件不要提交"的清单）。
**现在要不要管**：要。这是从第一天就得形成的肌肉记忆，不是以后再补的功课。

**3. 用量、费率与限流（rate limit）**
调 API 是按 token 计费的，而且平台会限制你每分钟能发多少请求、用多少 token。
**关系**：这是"调用大模型"这件事的成本侧和工程侧，跟功能侧一样重要。
**什么时候碰到**：Phase 02 做多步骤 agent 时会明显感觉到——一个流程调好几次模型，
成本和速度立刻变成要考虑的事。交付给客户时，"这套东西一个月要花多少钱"是必答题。
**现在要不要管**：知道有这回事就行。Anthropic 控制台里能看到用量，偶尔瞄一眼。

## Day 3 — 拆解昨天那个脚本

**目标**：看懂 Day 2 写的脚本每一行在做什么，而不是"能跑就行"。

不写新代码，让 Claude Code 带你逐行读 Day 2 的脚本，搞懂这几个问题：
- 这本质上是一次 HTTP 请求吗？发给谁？
- `messages` 里的 `role` 是什么意思，`user` 和 `assistant` 分别代表什么
- `system` 参数是干什么的，跟 `user` 消息有什么区别
- `model` 参数、`max_tokens` 参数分别控制什么
- token 是什么，为什么调用大模型是按 token 计费的

**今天的产出**：不是代码，是你能不看着答案，把上面五个问题口头讲一遍。

### 延展 · 你没问但该知道的

**1. SDK 和"直接发 HTTP 请求"是两条路**
我们装的 `anthropic` 包叫 SDK（软件开发工具包）——它把"拼 HTTP 请求、加认证头、
解析返回的 JSON"这些琐事包好了。不用 SDK 也能调，用 Python 的 `requests` 库或命令行的
`curl` 直接发请求，效果一样。
**关系**：SDK 是"发 HTTP 请求"这件事的便利封装，不是另一套机制。
**什么时候碰到**：调试时最常用——官方文档的例子经常给 curl 版本，能看懂 curl 就能对照
出"我的 SDK 调用到底发了什么出去"。
**现在要不要管**：不用动手，但今天拆解脚本时可以让 Claude Code 把同一个调用写成 curl
版本给你对照看一眼，"这本质上是一次 HTTP 请求"这句话会立刻变具体。

**2. 参数不止 model / max_tokens 两个**
常见的还有 `temperature`（控制回答的随机性，调低更稳定、调高更发散）、`stop_sequences`、
`stream`（流式返回，就是你在聊天界面看到字一个个蹦出来的效果）。
**关系**：都是同一个 API 调用上的旋钮，控制模型行为的不同侧面。
**什么时候碰到**：Week 3 做客服助手时会用到 temperature——客服场景要的是稳定一致的
回答，不是每次都不一样的发挥。
**现在要不要管**：不用。知道"旋钮不止这两个"就行，用到时再学。

**3. 提示工程（prompt engineering）是一门真手艺**
"怎么写 system 和 user 消息"这件事本身有大量方法论：给例子、让它分步骤想、明确输出格式。
**关系**：这是今天学的 system / user 参数的"用法层"——参数怎么填，比参数有哪些更值钱。
**什么时候碰到**：贯穿整个三个月。FDE 工作里，很多客户问题不需要写复杂代码，改好提示词
就解决了——这恰恰是"技术是手段，解决客户问题是目的"最直接的体现。
**现在要不要管**：不用专门学。后面每次调不出想要的结果，就是一次实战练习。

## Day 4 — 让它"记住"上下文

**目标**：写一个能连续对话的小脚本，同时搞懂它为什么"记得"。

- 关键认知：模型本身没有记忆，每次调用都是全新的。"多轮对话"是因为你把历史消息
  全部重新传了回去
- 写一个脚本，能连续问它三句话，且它答得出"你刚才说的第一句是什么"
- 想清楚：如果对话很长，历史消息会越传越大，这意味着什么（成本、速度、后面会学到的
  怎么控制上下文长度）

### 延展 · 你没问但该知道的

**1. 上下文窗口（context window）有上限**
每个模型能一次性接收的 token 数是有上限的，超了会报错。历史消息无限堆下去，迟早撞墙。
**关系**：这是今天"历史越传越大"这个认知的硬性边界。
**什么时候碰到**：Phase 02 的多步骤 agent，一个流程跑下来消息堆很多，就得处理这件事。
行业里的常见办法：只保留最近 N 轮、或让模型先把前面的对话总结成一段再往下传。
**现在要不要管**：不用。知道"有上限，撞到了有办法处理"就够。

**2. 「会话记忆」在产品里是另外做的**
你用的 ChatGPT / Claude 网页版能"记住你是谁"，不是模型本身有记忆，而是产品层面把你的
信息存在数据库里，每次调用前再塞进提示词。
**关系**：这是今天"模型无状态"这个核心认知的产品级延伸——所有看起来有记忆的 AI 产品，
背后都是这套把戏。
**什么时候碰到**：客户提"我要它记住每个客户的历史订单"这类需求时，你要立刻知道
这是数据库 + 检索的活，不是模型的活。这个判断力正是五步方法论里"判断 Architecture"那步。
**现在要不要管**：不用动手，但这个认知要牢牢记住，它会反复用到。

## Day 5 — 结构化输出

**目标**：让模型返回 JSON，而不是一段自由文本。

- 改写脚本，要求模型的回复必须是固定字段的 JSON（比如问它"这句话的情绪是正面/负面/中性"，
  让它只回 `{"sentiment": "..."}`）
- 想清楚为什么这件事对企业交付重要：下游系统（比如客服后台）要拿这个结果去做判断、
  存数据库、触发别的流程——不能是一段人读的散文，必须是程序能直接解析的结构

### 延展 · 你没问但该知道的

**1. 让模型输出 JSON 有好几种可靠程度不同的办法**
最土的是在提示词里写"只返回 JSON"（模型偶尔还是会加一句废话）；更可靠的是用 API 提供的
工具调用（tool use）机制，直接定义好字段结构让模型按格式填。
**关系**：都是解决今天这个问题，可靠性台阶不同。
**什么时候碰到**：Phase 02 的核心就是工具调用。今天先用最土的办法体会"为什么需要结构化"，
到时候再学正规做法，你会明白它好在哪。
**现在要不要管**：不用。今天用提示词做到就行，遇到它不听话反而是好事——那正是 Phase 02
要解决的问题的由来。

**2. JSON 是什么，为什么到处都是它**
JSON 是一种文本格式，用来表示"字段 + 值"的结构化数据。你已经见过它了：`flashcards.json`、
`progress.json` 都是。API 请求和响应也是 JSON。
**关系**：它是程序之间交换数据的通用语言，今天让模型输出 JSON 只是它无数用途之一。
**什么时候碰到**：天天碰到，贯穿全程。
**现在要不要管**：要，但不用专门学——多看几次就会了，它没有复杂语法。

**3. 「模型输出不可信」是要防的**
模型可能返回格式不对的 JSON、可能编造不存在的字段值。企业级交付必须假设它会出错。
**关系**：这是今天这个知识点的工程侧——拿到结构化输出不等于拿到正确输出。
**什么时候碰到**：Week 1 任务表里 Day 6 提到的"已知问题清单"、五步方法论里的"验收 Harden"
那一步，核心就是在处理这类事：解析失败怎么办？值不合法怎么办？重试还是报错？
**现在要不要管**：知道就行。但如果今天脚本跑出来的 JSON 解析失败了，别当成事故——
那是真实世界的样子，记下来。

## Day 6（周五）— 复盘 + 小测

- 自测本周的核心概念（对照本周闪卡，看能不能不查资料答出来）
- 把这周写的几个脚本，整理成一个文件夹，命名清楚，当作 Week 1 的产出留档
- 如果有卡住没搞懂的地方，标记下来，Week 2 开始前先解决，不要带着漏洞往下走

### 延展 · 你没问但该知道的

**1. `requirements.txt`：把依赖列表也留档**
在虚拟环境里跑 `pip freeze > requirements.txt`，会生成一个文件，记下这个项目装了哪些包、
什么版本。别人（或未来的你）拿到你的代码，`pip install -r requirements.txt` 就能一键
装齐一模一样的环境。
**关系**：venv 是"这台电脑上的独立环境"，requirements.txt 是"把这个环境的配方写下来"，
让环境可以在别的电脑上复现。
**什么时候碰到**：每一次交付。只给代码不给依赖清单，等于给了菜谱不给配料表。
**现在要不要管**：今天整理产出时顺手生成一个，是个好习惯的起点。

**2. 版本管理的真实用法：不只是备份**
Git 的价值不是"存一份旧的"，而是"任何一行代码,能查出是谁、什么时候、为了什么改的"。
**关系**：这是 README 里"版本管理 —— 专业交付最起码的可追溯性"那句话的实际含义。
**什么时候碰到**：Phase 02 开始，你的项目代码应该开始进 Git，而不只是本地文件夹。
**现在要不要管**：Week 1 不用。但可以让 Claude Code 带你把这周的脚本文件夹做一次
`git init` + 第一次提交，体会一下。

**3. 「学完就忘」是正常的，主动回忆才是解药**
每天推送的闪卡不是形式主义——它用的是"主动回忆"这个机制：**先自己想答案，再看解析**，
效果远好于反复重读笔记。
**关系**：这是整个手册"闪卡 + 每天 1 小时实操"节奏设计背后的依据。
**什么时候碰到**：全程。
**现在要不要管**：要。收到闪卡时，别急着看答案，先在脑子里答一遍——哪怕答错，效果也比
直接看答案好。

## Day 7（周末，轻量/可选）— 预习下周

不用动手写代码。花几分钟让 Claude Code 用大白话给你讲一遍：什么是检索增强（RAG）、
为什么客服助手需要它（模型本身不知道"你们公司的产品手册"里写了什么）。
建立概念就够，Week 2 正式开始搭建。

### 延展 · 你没问但该知道的

**1. 「让模型知道我们公司的资料」有三条路，RAG 只是其中一条**
① 直接把资料全塞进提示词（简单，但资料一多就撞上下文上限、且贵）；② RAG（检索出相关的
那几段再塞，我们要学的）；③ 微调 fine-tuning（拿自己的数据再训练模型，贵、慢、且不适合
经常变动的资料）。
**关系**：三条同类路线，解决同一个问题，代价和适用场景不同。
**什么时候碰到**：客户几乎一定会问"能不能让它学习我们的资料"。**能说清这三条路的取舍、
并给出选择理由，就是五步方法论里"判断 Architecture"那一步的实际内容**——这正是 FDE 值钱
的地方，不是会写代码，是会做判断。
**现在要不要管**：不用记细节。只要记住"有三条路、我们选 RAG、因为资料会变且量大"。

**2. RAG 背后会牵出向量数据库这个词**
检索"相关内容"靠的是把文字转成一串数字（叫 embedding 向量），再找数字上最接近的几段。
存这些向量的地方就叫向量数据库（Chroma、Pinecone、pgvector 等）。
**关系**：这是 RAG 的下一层实现细节。
**什么时候碰到**：Week 2 搭客服助手时就会碰到，到时候会带你实际用。
**现在要不要管**：不用。听到这个词不心慌就行，Week 2 会讲。

**3. RAG 不是万能的，它有典型失败模式**
检索没找到对的段落 → 模型答不出或胡编；资料本身写得烂 → 检索再准也没用。业界有句话：
垃圾进，垃圾出。
**关系**：这是 RAG 的局限侧，跟功能侧一样要早知道。
**什么时候碰到**：Week 3、Week 4 做验收时，你会亲眼看到它答错，那时候要能判断
"是检索错了还是资料本身有问题"。
**现在要不要管**：不用。但先有心理准备：**RAG 搭出来第一版答得不好是常态，不是你做错了。**
