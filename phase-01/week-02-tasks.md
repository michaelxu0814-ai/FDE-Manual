# Phase 01 · Week 2 — 让助手"读过"产品手册（检索增强 RAG）

场景延续：还是那家中型电商公司。上星期你学会了怎么调用大模型。但这周要面对一个真问题：
**模型本身根本不认识"你们的"产品手册。** Week 2 的目标是——让助手在回答前，先从手册里
"找到"相关的资料，再照着资料回答。这就是 RAG（检索增强生成）的最小版本。

每天 1 小时。做不完没关系，宁可少而扎实，也不要囫囵吞枣往下赶。

## Day 1 — 准备"知识库"：把手册变成能检索的东西

**目标**：建一份小小的产品手册文本，并写一个能"切块 + 读取"它的脚本。

- 随便选一个产品（虚构的也行，比如 "AuraPod S2 便携蓝牙音箱"），用中文写一份 20 段左右的
  产品手册/FAQ：功能、参数、常见问题（怎么开机、怎么连蓝牙、怎么充电、坏了怎么保修……）。
  让 Claude Code 帮你起草，但你要读一遍、改一遍——这是客户的原话，你要能读懂它。
- 关键概念：**为什么不能把整本手册直接塞给模型？**（token 成本高、内容太长容易答偏、
  改一个字就得重传全部）。所以要"切块"。
- 写一个脚本：把手册按段/固定字数切成一列"小块"（chunk），打印出来数一数有几块。
- 让 Claude Code 带你读脚本，搞懂"读文件 → 切块 → 打印"这三步各在干什么。

**今天不需要懂**：embedding、向量、相似度。那是 Day 6-7 的预告。

## Day 2 — 第一次"检索"：从手册里挑出相关的几段

**目标**：用户问一句，脚本能从几十块里挑出最相关的 1-2 块。

- 最朴素的检索：**关键词匹配**。把用户问题里的词，拿去和每一块比对，哪块命中词最多就选哪块。
- 写/改脚本：输入"怎么开机"，输出它认为最相关的 1-2 块内容。
- 想清楚：RAG 的 R（Retrieval，检索）这一步，**产出的是"资料"，不是"答案"**。答案要等模型来写。

**今天不需要懂**：为什么关键词匹配不是最好的办法。先让它能用。

## Day 3 — 把资料交给模型：第一个 mini-RAG 跑通

**目标**：检索 → 拼进提示 → 模型在资料范围内作答，一条线串起来。

- 组合 Day 2 的检索结果和 Week 1 的调用能力：把挑出来的那 1-2 块，作为"参考资料"放进
  发给模型的 messages 里（放在 user 消息里，或 system 里声明"以下是产品手册片段"）。
- 测试：问"怎么连蓝牙"，看模型是不是照着手册片段答，而不是瞎编。
- 想清楚：为什么说"模型本身不知道你们的产品手册写了什么"——它只看得见你这次发给它的东西。

## Day 4 — 管住它：答不上来就直说，别编

**目标**：把"幻觉"压下去，这是企业客服的底线。

- 在 system 或提示里加规则："只根据提供的资料回答；资料里没有，就明确说不知道，并建议联系客服。"
- 故意问一个手册里没有的问题（比如"防水等级是多少"），看模型是不是老实说不知道。
- 概念：幻觉（hallucination）就是模型一本正经地编。客服场景里客户拿它当回事，一次编造可能砸掉一个客户。
- 进阶（可选）：让它回答时带上出处（"根据手册第 5 节"）。

## Day 5（周五）— 复盘 + 小测 + 归档

- 自测本周核心概念（对照本周闪卡，不查资料答一遍）。
- 把 Week 2 的脚本整理进 `fde-week2` 文件夹，写一行注释说明每个文件是干嘛的。
- 没搞懂的地方标下来，Week 3 前先解决，不要带着漏洞往下走。

## Day 6-7（周末，轻量/可选）— 预习

- 想一个问题：如果手册有一万块，挨个做关键词匹配太慢、也太不聪明。业界怎么解决？
  （提示：把"文字"变成"数字向量"，找"意思相近"的块。不用动手，让 Claude Code 用大白话讲给你听。
  Week 3 会用到。）
